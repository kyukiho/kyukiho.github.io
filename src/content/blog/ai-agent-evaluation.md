## 前言

笔者在薯厂做了三个月 AI Agent 评测，工作包括构建 benchmark、归因沉淀 bad case，以及设计和搭建评测框架。结合前期调研与实际经验，本文整理一套评测 Agent 的思路。

## 评测指标的定义与设计

Agent 评测既要看任务结果，也要看完成任务的过程。不同指标回答的问题不同，不能只用一个总分概括所有能力。

### 结果指标

结果指标从最终验收角度评估任务是否成功，常见指标包括：

- **Pass@1**：单次执行成功率，反映 Agent 一次完成任务的即时表现。
- **Pass@k**：k 次尝试中至少成功一次的比例，反映能力上限。
- **Best@k**：k 次尝试中的最高得分，用于观察多次尝试下能达到的最佳表现。
- **Pass^k**：k 次尝试必须全部成功，衡量业务可靠性与稳定性。

实际使用时，模型选型可以看 Pass@k，Prompt 调优可以看 Best@k；生产部署前应验证 Pass^k，日常运营监控则可通过 Pass@1 跟踪即时表现。

### 过程指标

过程指标从完整会话中评估 Agent 的执行行为，包括合法性、工具调用正确率和路径效率等。

- **行为合法性**：任务过程中是否出现无效操作或越权操作。
- **工具调用正确率**：查询工具是否准确表达需求，文件操作是否指向正确目标。
- **路径效率**：统计思考、行动、观察循环次数，冗余动作（如反复搜索相同关键词、重复读取同一文件）和回退次数。回退次数还可以反映 Agent 发现错误并纠正的频率。
- **检索覆盖率**：检查是否全面收集了完成任务所需的信息。

### 其他类型指标

也可以根据产品需要衡量成本、延迟和鲁棒性：

- **成本与延迟**：请求次数、Token 花费、任务完成时间等。
- **鲁棒性**：不同初始化条件下表现的差异、页面变化后的适应性、对 API 抖动的容忍度，以及长时间记忆是否受到干扰。
- **安全问题与幻觉**：这类指标通常具有一票否决性质，应严格检查敏感操作、数据外泄、违规内容，以及编造不存在的信息。

### 指标设计总结

1. 同时覆盖执行轨迹和最终结果。
2. 安全性指标可以设置为一票否决项。
3. 除正向标准外，也要定义失败与陷阱案例。
4. 结合人工抽检和对抗式评审，主动构造评判模型已知偏见可能给出高分的回答。

## 评测环境的设置

一个可复现的 Agent 评测环境由五部分组成：

1. **数据集**：定义任务集合，包括初始状态、目标描述和可选参考解法。
2. **环境状态**：任务执行中可能变化的信息。
3. **工具接口**：Agent 可以执行的操作集合。
4. **评分标准**：定义如何检查任务结果和执行过程。
5. **执行协议**：规定交互方式与任务终止条件。

这五个部分合起来构成一轮可重复的评测循环。环境状态要兼顾真实性与可控性：既符合业务逻辑，又能在每次测试前恢复到相同的初始状态。工具接口不应只提供“解决用户问题”这类过高层抽象，而应暴露查询订单、修改预订、发送邮件等原子操作，让 Agent 通过规划组合完成任务。评分标准可以是二元、连续或多维的。

### 两类评测环境

- **工具调用型环境**：通过调用预定义工具完成任务，按可执行标准验证结果，不依赖人工标注或模型评判。
- **人机交互型环境**：在自动化环境中模拟真实用户，适用于更开放、需要沟通澄清的任务。

前者可以参考 Verifiers 一类框架，但对复杂 Agent 的适用性有限，较适合目标单一、输入输出明确的任务。下面重点讨论人机交互型环境。

### 模拟用户与渐进式信息披露

普通用户通常不会一开始就说清任务的全部要点，Agent 需要通过主动提问逐步澄清需求。可以使用 `τ-bench` 的做法，让另一个 LLM 扮演用户：按预先定义的指令逐步透露信息、回应追问，并在任务完成后终止交流。

提示词应明确要求模拟用户不要一次性透露所有信息，并设置有限耐心：如果 Agent 沟通效率过低，就结束交互，记录任务失败。最终评测可以同时覆盖两种视角：端到端结果考察 Agent 是否正确完成行动，轨迹分析考察沟通策略是否合理。任务层面的最终结果可汇总为二元奖励，方便统计 Pass^k。

## 评测任务集的设计

### 精确性设计

任务应有可验证的目标，减少描述歧义。可以从以下几个方面设计：

1. **用答案唯一性反推描述**：通过信息来源、时间范围、主题和查询目标等约束，尽量锁定唯一答案。
2. **用信息分层承载真实语境**：每个任务可以包括表面问题、性能期望、约束条件和隐含情绪。例如，用户可能表达“移动数据无法工作”，同时提出“希望尽快修好”，并明确“不接受更换套餐”等约束。
3. **使用结构化字段与机械可验证元素**：问题描述、复现步骤、预期行为和实际行为都尽量结构化。测试用例中的每个要素应能被程序校验，例如路径是否存在、权限数值、证书参数和日期格式。
4. **用参数化模板替代静态文本**：把任务设计成可动态实例化的模板，每次生成不同参数，避免 Agent 记忆固定任务答案。
5. **从中间状态启动并显式消歧**：任务应从贴近真实使用的中间状态开始，而不是总从“干净”初始状态开始。

### 层次化设计

可以按技术难度和业务难度分级：

- 技术难度：例如 Level 1 需要多个工具，Level 2 需要多步思考，Level 3 需要复杂组合。
- 业务难度：例如 Level 1 是简单信息查询，Level 2 需要诊断故障，Level 3 需要进行整体策略判断。

实际分级通常需要综合技术复杂度与业务复杂度。

## 自动化评测方案：LLM-as-a-Judge

### 适用场景与局限

当任务没有标准答案、难以构造工具调用型环境时，可以使用人工评估；但人工评估难以规模化。LLM 评审可以帮助自动化评分，但不能忽视其偏差与局限：

1. **长度偏见**：可能更倾向于给较长回答高分。
2. **波动性**：相同输入多次评测可能得到不同结果。
3. **同源模型问题**：Agent 与评审模型属于同一家族时，Agent 可能迎合评审模型的偏好或盲点，绕开评审模型不擅长发现的错误。
4. **位置偏差**：在成对比较中，评审模型可能系统性偏向先出现的候选答案。

### Rubric 四准则

设计评审 Rubric 时，可以遵循四条原则：

1. **基于专家指导**：评审标准应反映领域知识；缺乏专业基础的 Rubric 往往只能评价语言流畅度等表面特征。
2. **全面覆盖**：覆盖事实准确性、逻辑连贯性、完整性和安全性；既定义正面标准，也明确陷阱。
3. **设置重要性权重**：区分必要项、重要项、可选项和陷阱项，并支持一票否决。
4. **自包含**：每项标准都能独立执行，不依赖评审者补充未提供的信息。

### 失败归因

bad case 可以来自用户明确纠正、用户抱怨或负面反馈，也可以由事后的状态检查、规则验证器或 LLM 评审发现。

归因记录应尽量结构化，至少包含引用的具体步骤号、工具名和观察证据；区分根因与结果；判断问题是否可恢复；并给出置信度。多个类别同时出现时，以“最早且能解释后续失败”的原因作为主因，其余记录为次因。

LLM 可以帮助把归因流程规模化，但不应完全依赖它。失败归因往往反映产品问题，而不仅是技术问题。保存案例时，应将任务目标、环境状态、Agent 与工具版本、完整执行轨迹一起归档，以便后续复现测试。

## 两层回归任务

- **端到端回归任务**：从初始状态和用户请求开始跑完整流程，检查最终状态、必要输出和安全条件。它最接近生产结果，但难以定位具体失败步骤。
- **轨迹前缀回归任务**：冻结首次错误之前的上下文、对话、工具返回和环境状态，只要求 Agent 继续执行下一步或几步，并观察其行为。成本较低，可以隔离单个策略或工具问题。对生产级、高可靠 Agent，这一层往往比端到端回归更重要。
