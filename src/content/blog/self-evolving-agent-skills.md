## 问题：静态配置难以适应变化

许多 Agent 的提示词、工具和工作流由人手工配置，部署后基本保持不变。这样的系统很难把真实执行中积累的经验转化为稳定能力：遇到新任务时仍要从头摸索，遇到环境变化时也未必能及时调整。

“自进化”试图让 Agent 在执行中积累经验，并把经验沉淀为可复用、可检索、可验证、可淘汰的知识资产。常见载体包括 Markdown 规则、可调用的 Skill，甚至 Agent 自己维护的代码。与微调相比，这类方式不必改动模型权重，更新也更容易检查、回滚和迁移；与只记录事实的记忆相比，Skill 更关注“怎么做”：例如某类任务按 A→B→C 执行，遇到 D 则先检查某个条件。

这里的“自进化”并不意味着系统能无约束地自我改写。有效的经验必须能被观察、测试、审查，并且在失败时可以撤回。

## 一个反馈闭环

可以把自进化系统抽象为四个部分：

```text
系统输入 → Agent 系统 → 执行环境 → 优化器
    ↑                              │
    └────────── 反馈信号 ──────────┘
```

这个闭环需要回答三个问题：

1. **优化什么？** 提示词、Skill、工具、工作流、记忆，还是模型权重？
2. **依据什么信号优化？** 人类反馈、单元测试、运行时错误、任务结果或 benchmark 分数？
3. **如何证明改进有效？** 通过独立验证、回归测试和必要时的回滚，确认新版本确实更好。

只收集反馈并不等于完成进化。若没有验证，系统可能只是把偶然成功误当成规律；若没有淘汰机制，新的经验还会不断堆积，反过来干扰后续任务。

## 几条常见技术路线

### 1. 增量更新上下文

把上下文当作一本不断补充的“战术手册”，让 Agent 在生成、反思和汇编等阶段更新其中的经验。这条路线实现直接，但容易出现两类问题：

- **越写越短**：反复压缩或重写时产生 brevity bias，关键步骤和适用条件被省略。
- **知识坍塌**：多轮改写导致原始细节逐渐丢失，甚至让后续版本偏离已验证事实。

因此，上下文更新最好采用增量方式，保留来源和版本；对重要条目记录适用范围，而不是反复用一段新总结覆盖旧内容。

### 2. 建立 Skill 库

Skill 库把验证过的动作序列封装成可检索、可调用的程序或说明。新任务到来时，Agent 可以先检索已有 Skill，再按当前情境执行或组合。成功经验由此成为能够复用的“做法”，而不只是一次会话中的回忆。

相关工程化探索包括 Alita 所代表的最小预定义与按需扩展思路，以及 MUSE-Autoskill 提出的 Skill 生命周期管理：创建、记忆、管理、评估和精炼。Skill 还可以附带“技能级记忆”，记录它在哪些场景成功、哪些条件下失败，并通过单元测试和运行反馈持续校正。

### 3. 让 Agent 修改自己的代码

另一条路线允许 Agent 使用编码工具修改自身源码或配置。SICA 展示了 Agent 借助编码工具编辑自身的方向；Darwin Gödel Machine 则通过维护 Agent 档案、采样变体并用 benchmark 做经验性验证，探索开放式演化。

这类方法的重要设计不只是“能改代码”，而是把候选版本放入可比较、可追踪的过程：记录改动、运行验证、保留分支，并在表现变差时恢复。每一步不必都能证明有益，但至少应当可测量，且避免只追求局部指标而损害整体能力。

### 4. 用强化学习内化技能

只靠 prompting 和外部 Skill 库，技能的调用与执行可能不够稳定。SAGE 等研究探索了用 GRPO 一类强化学习方法训练 Agent 连续执行相似任务：前面任务产生的 Skill 供后续任务使用，并把 Skill 是否被正确整合纳入奖励信号。

这条路线把部分经验从外部记忆移入模型策略，但训练成本、奖励设计和泛化效果都需要单独评估。它与外部 Skill 库并非只能二选一：外部知识便于检查和更新，模型内化则可能提高连续执行时的稳定性。

## Skill 应该如何治理

Skill 会增长、互相冲突，也会过期。因此，一个可持续的系统需要把知识治理作为独立环节：

- **检索排序**：根据任务、上下文和适用条件选择相关 Skill，避免把无关知识塞进提示上下文。
- **使用统计**：记录调用频次、成功率、失败类型和最近验证时间。
- **冲突处理**：发现规则矛盾时，明确优先级或将它们拆分到不同适用场景。
- **淘汰机制**：低使用率、长期未验证或表现持续变差的 Skill，应进入复核或删除流程。
- **版本与来源**：保留创建依据、修改记录和验证结果，让团队成员知道这条做法从何而来。

这也是为什么“汇编”或“策展”值得成为一个独立职责：重点不只是不断生成新技能，还要维护一套可用、可理解的技能集合。

## 落地时的四个问题

### 写什么

优先沉淀**可迁移的做法**，而不是一次性的事实。一个简单判据是：换一个任务，这条经验是否仍然有用？如果答案是否定的，它可能更适合放在任务记录里，而不是通用 Skill 中。

### 什么时候写

失败后刚刚修复成功的时刻，往往包含最多有用信息：失败条件、原因、修复动作和验证结果都还清晰。单纯记录成功过程通常不够，因为成功没有暴露边界条件。

### 如何验证

没有验证的自进化很容易变成放大幻觉。给每个 Skill 配置单测或回归用例，每次修改后运行；同时保留代表性任务，确认新版本没有损害原有能力。根据风险不同，可以采用自动验证、人工抽检或分阶段上线。

### 如何删除

技能可能膨胀、冲突和过期。结合检索排序、使用统计与定期淘汰，防止上下文被低价值技能挤满。删除之前保留版本或归档记录，以便发现误删时恢复。

## 安全边界

两条底线尤其重要：

1. **在沙箱中执行。** 对自改代码或自造工具的行为进行隔离，限制文件、网络和凭证访问，并保留可审计的执行记录。
2. **由人审核关键变更。** 自改代码和新造工具必须能查看差异、能回滚；高影响操作不应只凭 Agent 自己的判断自动生效。

安全控制不是进化完成后的补丁，而是反馈闭环的一部分。它决定了系统可以尝试什么、哪些结果能够进入知识库，以及谁有权批准变更。

## 小结

自进化 Agent 的核心，是把执行经验变成有边界、有证据、可复用的知识，再用反馈持续修正它。增量上下文、Skill 库、自改代码和强化学习分别作用于不同层次；实践中可以组合使用，但都离不开评估、版本管理、淘汰和回滚。

因此，衡量一个系统是否真正“越用越强”，不能只看它是否记住了更多东西。更重要的是：新经验能否迁移到新任务，改动是否经过验证，错误知识能否被识别和删除，以及团队是否能理解并控制整个演化过程。
